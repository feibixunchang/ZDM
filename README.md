# ZDM — 跨平台多线程下载管理器

本地版的 [NeatDownloadManager](https://www.neatdownloadmanager.com/) 克隆：多线程分块下载、断点续传、暂停/继续、队列、限速，并自带浏览器扩展接管下载。

支持 **Linux / macOS / Windows** 三端，零依赖（仅标准库 + 桌面端 PyQt5；`sftp://` 通道另需
`paramiko`，安装包已内置），安装后重装系统重装仍可用。下载协议覆盖 **http/https/ftp/ftps/sftp**。

当前版本：**v1.18.15**（桌面端与后端同一套版本号；浏览器扩展独立为 1.5.x）

## 仓库结构

| 路径 | 说明 |
|---|---|
| `zdm/` | 完整源码（引擎、服务、CLI、桌面端、浏览器扩展、安装脚本） |
| `zdm/zdm_launcher.m` | macOS 原生 App 启动器源码（`install.sh` 用 clang 编译成 `ZDM.app` 主程序） |
| `windows-native/` | 旧的 Windows C#/WPF 客户端（仅参考/回退，不再构建；Windows 已改用 PyQt5 那一套） |
| `dist/` | 三端正式安装包 |
| `docs/` | 安装与使用说明文档 |
| `build_dist.py` | 打包脚本：重新生成 `dist/` 下各平台安装包 |

## 安装包（推荐从 [Releases](https://github.com/feibixunchang/ZDM/releases) 下载）

| 平台 | 安装包 | 安装方式 |
|---|---|---|
| macOS | `ZDM-<version>-arm64.dmg` | 双击挂载，把 `ZDM.app` 拖进 Applications（内含扩展与中文说明）。**每个 Release 只构建 Apple Silicon 那一份**；Intel 机器请用下面那行从仓库安装 |
| macOS（Intel / 源码） | 仓库里的 `zdm/install.sh` | `git clone` 后 `cd zdm && bash install.sh`，自动生成 `ZDM.app` + 登录自启。这个脚本**不随任何安装包发布**，只从仓库取 |
| Linux | `zdm_1.18.15_amd64.deb` | `sudo apt install ./zdm_1.18.15_amd64.deb`（自带 Python + PyQt5，无需联网装依赖） |
| Linux | `zdm-linux-amd64.tar.gz` | 免 root：解压后 `./install.sh`，装到 `~/.local` |
| Windows | `ZDM-Setup-1.18.15.exe` | 双击安装（用户级、无需管理员、不依赖本机 Python，与 mac/Linux 同一份界面）；**软件内可直接一键更新** |
| 浏览器扩展 | 随上面各包附带 | Windows 装在 `{app}\extension`；macOS 在 `~/Library/Application Support/ZDM/extension`；装好后在 `chrome://extensions` 加载已解压的扩展程序 |

> **完全自动构建**：`.deb` / `zdm-linux.tar.gz` 在 `ubuntu-22.04` 上构建，
> `ZDM-<version>-arm64.dmg` 在 `macos-latest` 上构建，`ZDM-Setup-*.exe` 在 `windows-latest` 上构建（由
> `.github/workflows/build-packages.yml` 驱动），push main 即构建，推 tag 时产物自动挂到对应 Release。
> 每个 tag 的 Release 上就是四个文件：arm64 dmg、amd64 deb、linux tar.gz、Setup.exe
> —— 没有 x64 dmg，也没有 `zdm-macos.zip`。
>
> macOS 的 `.dmg` 与 Linux 的 `.deb` 都是**自包含**的：Python 运行时、PyQt5/Qt 与资源全部
> 打包在产物内，目标机器无需预装 Python、pip 或 `python3-pyqt5`。
> CI 在发布前会自检：macOS launcher 必须是 Mach-O 且 dyld 能解析内嵌 framework；
> Linux 的 `ZDM` 必须是 ELF、`--selfcheck` 必须报告内嵌 PyQt5/资源齐全、
> 所有 `.so` 无未解析依赖，并在 xvfb 里真实启动 GUI；`.deb` 还会在干净容器里
> `apt install` 一次再跑同样的自检。

每个包内自带 `extension/` 浏览器扩展，装完在 `chrome://extensions` 加载即可接管下载。
Firefox 也吃这同一份源码：桌面端「浏览器扩展」对话框里点「导出 Firefox 扩展」拿到 `.xpi`，
再到 `about:debugging#/runtime/this-firefox` → 「加载临时附加组件…」选中它（详见
`zdm/README.md` 的 Firefox 一节）。

> macOS 用户注意：`~/Library` 默认隐藏，在「加载已解压的扩展程序」的选文件夹窗口里按
> `Command + Shift + G`，粘贴 `~/Library/Application Support/ZDM/extension` 即可直接定位。

## 构建

```bash
python3 build_dist.py   # Linux .deb / tar.gz + macOS zip + （在 Windows 上）ZDM-Setup-*.exe

# 只做 Linux 原生包（自带 CPython + PyQt5 的 ZDM onedir + .deb + 免 root tar.gz）
bash zdm/build_linux_app.sh ./linux-build 1.18.15
```

> Windows 只有一个安装包：**`ZDM-Setup-*.exe`**（约 100 MB，自带 CPython 与 PyQt5，
> 用户机器上不需要装 Python）。它和 macOS / Linux 用的是**同一份界面和同一个下载引擎**。

## Windows 客户端

Windows 端从 v1.15.0 起与 macOS / Linux **完全同一份代码**：
`gui.py` + `theme.py` + `zdm/` 引擎，由 `zdm/zdm.spec`（PyInstaller）冻结成 onedir，
再用 Inno Setup 封成安装包。构建脚本 `zdm/build_windows_app.ps1` 一条命令跑完。

> 为什么不再是独立的 C#/WPF 客户端：那套实现自带下载引擎和 HTTP API，
> 等于把同一个功能写了两遍。结果是 mac 上修好的 YouTube 解析、探大小、DASH 音频合流，
> Windows 一行都没生效。`windows-native/` 仅作为参考/回退保留，不再参与构建。

安装包为用户级安装（`%LOCALAPPDATA%\Programs\ZDM`，**不需要管理员权限**），装完自动完成：

- 注册 `zdm://` 协议，浏览器里点链接可直接把下载任务交给 ZDM；
- 注册 Chrome / Edge / Chromium / Brave 的 **Native Messaging** 宿主（`com.zdm.launcher`，
  指向随包的 `ZDM-NativeHost.exe`），**ZDM 没运行时**扩展一点下载就能把它拉起来；
- 把浏览器扩展解压到 `{app}\extension`，扩展的落盘路径由安装包保证；
- 「开机自启」写 `HKCU\...\Run`，值与程序内开关用的是同一条命令（`ZDM.exe serve`）。

**为什么是 Native Messaging 而不是 `zdm://`**：Chrome 只在**有用户手势**的页面里才允许跳转外部协议，
扩展自己开的隐藏标签页没有手势，`zdm://` 导航会被静默丢弃。所以扩展先
`chrome.runtime.connectNative("com.zdm.launcher")`，`zdm://` 只作兜底。

构建（在 Windows 上）：

```powershell
# venv + PyQt5 + PyInstaller + 下载 bin/yt-dlp.exe 与 bin/ffmpeg.exe + 冻结 + 自检 + 打安装包
powershell -ExecutionPolicy Bypass -File zdm\build_windows_app.ps1 -OutDir dist
```

依赖：Python 3.9+、网络可访问 PyPI 与 GitHub、Inno Setup 6（`iscc`）。
版本号唯一来源是 `zdm/zdm/__init__.py` 的 `__version__`，脚本自己读取，不需要手动对齐。

**升级提示**：扩展文件装在 `{app}\extension` 里，跨版本升级时该目录会被重写。
升级前先退出 Chrome，否则 Chrome 可能在目录重建的瞬间把扩展条目丢掉。

## 故障排查

**浏览器扩展怎么装？** 桌面端工具栏和托盘菜单都有「浏览器扩展」入口：它同时显示
①扩展是否已加载（由扩展发给本机服务的 `GET /api/extension/ping` 心跳回答，而非去猜
注册表/浏览器配置）、②一键打开扩展目录、③三步加载说明（`chrome://extensions` →
开发者模式 → 加载已解压的扩展程序 → 选扩展目录）、④**Firefox**：同一份源码现打成
`.xpi` 的「导出 Firefox 扩展」按钮（Firefox 没有「加载已解压的扩展程序」，只能装包）。

**Windows 安装后打不开，报「Failed to load Python DLL '_internal\python312.dll' —
LoadLibrary: 内存资源不足」** —— 这**不是真的内存不足**（32G 也会报）。
v1.15.13 之前的真正根因是**进程无限拉起链**：`desktop.py::ensure_desktop` 拉起
窗口时漏传 `--gui`，冻结版 exe 只好落到 CLI 分支又再次拉起，十几秒堆出几十个
进程把资源耗尽，`LoadLibrary` 才报内存不足（事件查看器里是 ucrtbase.dll
BEX64 / 0xc0000409）。**升级到 v1.15.13 及以上即可根治。**

如果你停留在旧版本，两大环境因素也会触发同样的报错：

1. **杀毒软件在安装过程中隔离/篡改了 DLL**：打开杀毒软件的隔离区还原文件，
   并把 ZDM 安装目录加入信任/排除列表。v1.15.3 起安装器在装完时会自动跑一次
   `--selfcheck` 自检，失败当场弹出带处理指引的对话框，不用等第一次双击才发现。
2. **系统页面文件（虚拟内存）被关闭**：在「系统属性 → 高级 → 性能设置 → 虚拟内存」
   恢复为自动管理后重启。

处理后重新运行安装包覆盖安装一遍即可。

**视频下载失败（YouTube 转圈/报 403/提示人机验证/"The page needs to be reloaded"）** ——
v1.15.15 修了重试客户端与直链兜底，v1.15.16 补上了**真正的常见根因**：

1. **缺少 JS 运行时**。2026 年起 yt-dlp 要跑 YouTube 播放器里的 JS 解签名和
   n 参数；没有 deno 时 YouTube 只回故事板，yt-dlp 的报错却是毫不相干的
   "The page needs to be reloaded"。**v1.15.17 起 Linux / macOS 安装包已内置
   deno 2.9.8**（`_internal/bin/deno`，优先于系统版本），装完即可用，不需要
   用户自己安装。源码运行时仍会按 PATH、`~/.deno/bin`、`~/.local/bin`、
   `/usr/local/bin`、`%USERPROFILE%\.deno\bin`、`%APPDATA%\npm` 等目录查找；
   都找不到时会在任务报错里直接写「缺少 JS 运行时」，不再让你去猜 Cookie。
2. **升级后旧服务进程还在跑旧代码**。后台 `serve` 是独立进程，覆盖安装只换了
   磁盘文件；界面是新版、下载引擎还是旧版，于是 "更新了还是老毛病"。
   v1.15.16 起 GUI 启动时会对比 `/api` 报告的版本，不一致就请旧服务退出并
   拉起当前版本；Linux 的 .deb/tar.gz 现在会同时结束 `/opt/zdm/ZDM` 与
   `/usr/bin/zdm-desktop`（旧界面），Windows 安装包也会在安装前结束旧进程。
3. **重试客户端与兜底**（v1.15.15）：`android_vr` 已失效，换成 `tv_embedded`；
   yt-dlp 通道全灭时不再被 403 挡住，直接切到解析出的直链用内置引擎下载。

> 如果报错是 `Sign in to confirm you're not a bot`：这是 YouTube 在要求登录态，
> 而浏览器导出的 Cookie 已被判定失效（YouTube 会定期轮换 `SID`/`PSIDTS`，甚至
> 几分钟就换一次）。处理：在 Chrome 里打开并登录 YouTube（把那支视频播几秒），
> 再用扩展的「下载此视频」重试；或在设置里粘贴**刚导出**的 Cookie。部分视频
> （年龄限制、会员内容）匿名永远拿不到，必须登录。
> v1.15.16 起这种情况最多重试两个客户端（约 30 秒）就会给出中文提示，不再让你
> 盯着 0% 干等一分多钟。

**粘贴视频链接却下到了网页（文件名是 watch）** —— 这是页面链接被当普通文件
下载了（下完是一个 HTML）。v1.15.16 起，YouTube / B站 / 抖音等**页面链接**
在桌面端、网页版、命令行都会被自动识别成「页面任务」，交给 yt-dlp 解析成
真正的视频；YouTube 还会先让你选清晰度。媒体直链不受影响。

**v1.15.17 补充**：网页版 / `zdm add` 粘贴视频页面时也会得到带扩展名的
文件名（以前可能是一个没有后缀的 `download`）；YouTube 清晰度默认选
1080P（不再默认最高档，避免误下 4K）；JS 运行时探测补上 `~/.local/bin`。

**v1.15.18 补充**：
- 更新下载前并行测速 GitHub / 公共镜像，自动选最快线路（国内直连常只有
  几百 KB/s）；更新横幅新增「打开发布页」，可交给其它下载工具。
- 下载完直接拉起系统安装器：Linux 打开系统包安装器，Windows 显示安装进度，
  不再二次确认，也不会「下载完什么都没发生」。
- 主界面常驻「扩展已连接」状态；扩展心跳改为 1 分钟，桌面端升级后自动
  reload 扩展，不需要重开浏览器。
- 工具栏「＋下载」在有链接时直接进清晰度选择，只弹一次窗。
- Linux「打开 / 目录」改用 GUI 会话唤起，修复后台服务没有 DISPLAY 导致
  按钮点了没反应；Windows 正文字体统一雅黑 10pt + 整数缩放，减少发虚。

**改了设置却没生效** —— v1.16.4 起配置先整批校验、再一次性落盘：

- 布尔开关认 `true/false/yes/no/on/off`。`zdm config mirror_accel off` 现在是真
  关掉；以前 `bool("off")` 等于 True，开关会被写成反的。
- 数字项认 `"16"` 这类字符串写法，并加了区间：连接数 1~32、同时任务数 1~32、
  端口 1~65535、限速 ≥0、超时 1~3600。网页版把输入框**清空**时 `Number('')`
  是 0，以前会照样存进去（下载退化成单线程、队列直接卡死），现在保存前就按
  字段名提示「单任务连接数 要填数字」。
- 下载目录不许留空；目录建不出来（没权限）当场报错，不会留下半新半旧的配置。
- 写坏一项（`speed_limit fast`）服务端回 400 并指名是哪一项，CLI 退出码 1，
  桌面端状态栏和网页版给中文提示，同一批里其它项也不会被偷偷改掉。
- 老版本存下的、或手工改过的 `state.json` 里越界的值也不再原样生效：读回来时
  数字夹回区间（`max_active=-5` 曾让队列永远起不来、`500` 会一口气开几百个线程），
  类型写坏的（`connections:"abc"`）退回默认值，端口越界退回 9000 —— 启动时能跑
  起来比报错更值钱，这些兜底在三端（桌面/网页/命令行/扩展）共用同一张区间表。

端口改动仍需重启服务才生效。

**历史任务凭空少了几条** —— v1.16.7 起，读取任务记录时按同一套规则兜底：

- `state.json` / `.zdm-meta` 里被写坏或改坏的数字（`connections:"abc"`、
  `priority:999999`、`size:null`）读回来时退回默认值或夹回区间，不再因为一次转换
  失败让整条任务消失；越界的老优先级会被夹到 ±99，不会一直插队。
- `created_at` / `completed_at` 是队列排序和历史裁剪的键：以前混进字符串会让调度器
  每轮抛异常、所有任务都不开工，现在这类键保证是数字。
- 断点分块（`chunks`）坏几块只跳过那几块，超出文件长度的块不再被相信（否则连接会
  往 EOF 之后写）；全坏就当没有断点，重新分段下载。
- 「检查更新」的版本号只认每段开头的数字：`1.16.7-rc2` 不再被算成 1.16.72，
  四段的 `1.16.7.1` 也能认出比 `1.16.7` 更新。

**点了按钮却什么都没发生** —— v1.16.8 起，这三端共用的失败不再被说成成功：

- `state.json` 解析不了时先把原件备份成 `state.json.bad-<时间>`，再把原因写进
  `download-errors.log`；`save_state` 没落盘（目录只读、磁盘满）会记在 `state_error`，
  `/api/state`、`/api/config`、`POST /api/tasks` 的响应都带 `warning`，桌面端状态栏直接显示。
  以前这两条都是静默的：一次坏解析当成「没有历史」，随后任何一次保存就把空列表覆盖回
  磁盘，下载记录从此消失且界面上没有痕迹。
- 开机自启核对 `launchctl bootstrap` / `load` 的退出码，拉起桌面端核对子进程的退出码：
  launchd 没接受这个启动项、或程序起来就非 0 退出（bundle 损坏、argv 拼错）时，复选框
  退回未勾选并写明原因，不再凭「配置文件写好了」显示「开机自启：已开」。
- 批量动作（全部暂停 / 全部继续 / 清除已完成）回 `changed`，也就是服务端真正改动的条数：
  0 条时界面说「没有正在下载的任务」，以前它和「已暂停 3 个任务」长得一模一样。
- 网页版 `api()` 统一兜底：连不上本机服务、返回 HTML（9000 端口被别的程序占了）、
  HTTP 5xx、以及 200 但正文不是 JSON，全部变成 `{ok:false, error:…}`。以前这些异常
  直接冒到调用方，点按钮的表现就是「没反应」。
- 浏览器扩展（1.5.41）交接前确认「这条是否已入列」时同时比对 `original_url`：开了镜像加速后
  `url` 被换成镜像地址，只比 `url` 永远查不到，同一个文件会被下两遍。
- `zdm config` 的未知键（`conenctions` 少打一个字母）回 400 并指名是哪一项，CLI 退出码 1；
  一批里混一个坏值则整批不生效。`zdm://` 链接添加失败（坏链接、服务没起、token 不对）
  同样写 stderr 并退出 1，不再是「双击链接什么都没发生」。
- curl 探大小以 `returncode` 为准：DNS 失败 / TLS 断 / 拒绝连接时 `-w` 模板照样打印出
  `http_code=000`，以前被当成一次正常探测，任务带着 `size=0`、不支持 Range 排队空转，
  很晚才报错。
- 桌面端「修改任务」对话框的连接数、优先级、定时开始统一走 `_num` / `_int`：记录里
  写坏的值退回默认，不会因为一次 `float()` 异常把整个对话框关掉。

`windows-native/`（C# 参考实现）同步了这些行为：批量动作回 `changed`、配置未知键报错、
`StateError` 透成 `warning`、开机自启校验注册表写入结果。**本机没有 dotnet，C# 侧未编译验证。**

**简介里显示的版本号和实际跑的版本对不上** —— v1.16.9 起，`install.sh` 把 bundle 的
`CFBundleVersion` 与 `CFBundleShortVersionString` 一起改写（改完照旧 ad-hoc 重签）：
装过 DMG 的机器上以前只改前者，源码同步了、`/api/state` 也报新版，但 Finder「显示简介」
和 App 「关于」读的是后者，本机它一直停在装 DMG 那一次的 1.15.39。版本号是照着
`download-errors.log` 排查时第一个要核对的东西，对不上就等于没有。（v1.16.8 的发布资产
里仍是旧脚本 —— tag 不能挪 —— 所以这一笔单独补成 v1.16.9。）

**m3u8 / mpd 下不动、下了只有一条** —— v1.17.0 起，HLS / DASH 交给内置的
**N_m3u8DL-RE**（MIT，随包单文件，无需 .NET）：按分片并发取、单片失败只重取那一片、
暂停后按分片续传（实测同一份 6 分片源，续传只补没下完的那片，0.1 秒收尾）。设置里
`stream_engine` 三端都能选：`auto`（默认，RE 失败自动换 ffmpeg 并把换的理由写在任务上）、
`re`、`ffmpeg`；界面状态列会显示这一条实际用了哪个引擎。

- 以前只能报「引擎退出码 1」：这个引擎最常见的死法（播放列表 404）压根不打 ERROR，
  而是每轮重试一条 WARN，最后甩一段 .NET 异常。现在失败原因取 ERROR 文案 → 异常首行
  加 `--->` 那句根因 → 最后一条 WARN，`流媒体下载失败（N_m3u8DL-RE）：… 404 (File not found)`
  这样能直接照着排查，`download-errors.log` 里也是同一句。
- 合流阶段（`ffmpeg merging...`）标成「合并中」，不再表现成「卡在 83% 不动」。
- 引擎自己那份分片暂存目录（`re-work/<任务 id>`）在暂停时留着续传，删除任务或
  「清除已完成/失败」时一并回收，不再在配置目录里留永久垃圾。
- 打包侧：`--selfcheck` 现在要求随包 N_m3u8DL-RE 存在**且能跑**（跑一次 `--version`），
  CI 额外校验 macOS 那份已签名、没有 quarantine 属性；`install.sh` / `install.ps1`
  里 deno 与该引擎各自补齐（以前 deno 在就整段跳过，升级上来的机器永远补不上流媒体引擎）。

**多音轨的 m3u8 下成「没声音的视频 + 一地散件」、轨道只能听引擎挑** —— v1.17.2 起，
HLS / DASH 能点名要哪几路轨，产物固定是**一个**能直接播的文件。

- **`-M format=mp4` 取代散件**：`--auto-select` 碰到多音轨的 master 会产出「仅视频的
  无声 mp4」+ `<主名>.eng.m4a` + `<主名>.spa.m4a` + `<主名>.eng.srt`，引擎自己不合流。
  现在每条命令都带 `--mux-after-done format=mp4`，由引擎收尾时混流并清掉中间产物。
  代价要说清：纯音频流（音乐站、播客）的容器从 `.m4a` 变成 `.mp4`（改名时仍以真正产出的
  容器为准，不会给你打不开的后缀）；混进 mp4 的轨道不再带 language 标签，字幕也进容器而不是
  留 sidecar，所以 `--sub-format` 只在容器里装不下那种字幕时才看得出差别。
- **轨道选择** `-sv` / `-sa` / `-ss`（值就是引擎的「子键=值，多个用冒号分隔」语法，如
  `lang="eng":codecs="mp4a"`，也可整体写 `all` / `best` / `worst1`）+ `--sub-format SRT|VTT`。
  给了任一项就**不再发 `--auto-select`**：实测两者同传时引擎照旧按 auto-select 下，显式选择被
  静默忽略 —— 用户勾了「只要西班牙语」却拿到默认音轨，比直接报错更难查。
- 入口有**语法**校验（桌面端新建/编辑对话框、网页版地址条下方的轨道条与编辑对话框、
  `zdm add --select-video/--select-audio/--select-subtitle/--sub-format`、`/api/tasks`）：
  打错的子键（`lagu=`）、换行/控制字符（不能借参数注入）、超长一律在建任务时就拒，网页版和
  CLI 直接看到中文原因（HTTP 400）。轨道**在不在**不在这里判 —— 那要联网解析播放列表，是引擎的活。
- **空白先抹掉**：`res = "1280"` 在引擎眼里不是 `res="1280"`，结果是命中 0 条轨道后甩一句
  英文 `No stream found to download`。输入框里多打一个空格很常见，这层归一必须在交引擎之前做完。
- 选 ffmpeg 引擎时给轨道**直接拒绝**（ffmpeg 通道看不懂选择器），而不是默默按默认轨下完再说
  「按你挑的做完了」；`auto` 退回 ffmpeg 时把这条一并写进 `stream_note`。
- 编辑任务改轨道会作废 `re-work/<任务 id>` 分片暂存：那些分片是按另一条轨的清单取的，留着续传
  等于把两次的结果拼在一个文件里。
- **粘贴 `.m3u8` / `.mpd` 地址现在自动认成流媒体任务**：以前调用方没给 `kind` 就走普通文件通道，
  把那几百字节的播放列表文本存成 `movie.mp4`，状态还是「已完成」——假成功。扩展与 yt-dlp 显式给的
  `kind` 照旧优先（DASH 的「视频轨 + 单独音频轨」要靠它走两段合流）。

**`.m3u8` 是「还在播」的直播时，只能眼巴巴看着它一直转圈、停了还没成品** —— v1.17.3 起，
直播流可以录制，而且**任何时候停都能保住已经录下的那一段**。

- **「是不是直播」不让用户填**：播放列表里没有 `#EXT-X-ENDLIST` 就是还在播（`.m3u8` 后缀本身
  说明不了什么，点播的回放片也是这个后缀）。这一步在**拼命令之前**问一次（`probe_live`）：
  等引擎自己打印 `Live stream found` 已经来不及，那时命令早发出去了。问不出来（网络挂了 /
  403）就按点播跑 —— 那是一直升级前的行为，不为了猜一把而把正常任务带进直播分支。
- **直播和点播是两套参数，不能共用**：点播必须发 `--mux-after-done`（不发就产出没声的散件，
  见上一条 v1.17.2），直播**绝对不能**发 —— 实测发了之后引擎一直 `Waiting`、进度报 100%、
  保存目录一个字节都不出来，因为直播永远等不到「下完」那一刻去触发收尾合流。直播改发
  `--live-real-time-merge --live-keep-segments false`，引擎把分片**边录边追加**到一份不断变长的
  `.ts` 上；ZDM 量这份 `.ts` 的大小得到「已下多少字节」，收工时用 `ffmpeg -c copy` 转封装成
  mp4（`+discardcorrupt`：被打断的最后半片默认会让 ffmpeg 直接报错退出；`+faststart`：
  下完就能边看边拖）。转封装做不到时（找不到 ffmpeg）保留 `.ts` 并把原因写在任务上，
  不假装成功。成品用用户给的文件名，不再自撞成 `xxx (1).mp4`。
- **录制时长上限**（`stream_live_limit`）：桌面端新建/编辑对话框、网页版地址条下方的轨道条与
  编辑对话框、CLI `zdm add --live-limit`、`POST /api/tasks` 都收同一项；写 `900`、`15:00`、
  `1:00:00` 都行，留空 = 一直录到手动停止或直播自己结束。超过 24 小时**报错而不是夹住**：
  夹住会让人以为正在录第 25 小时，而那一段根本不会开始。
  站点行为要说清：`--live-record-limit` 按**内容时长**计，且很多直播站只保留最近几十秒的分片 ——
  上限设得比站点窗口短并不会「只下这么长」，站点窗口比上限更短时反而会录满整个窗口。
- **直播没有「暂停」**：分片的边缘已经过去，挂起之后无从续传。所以每一个「暂停」入口
  （网页/API 的暂停、桌面端「全部暂停」、退出应用时的收尾）在录制中都一律等于
  **停止录制** → 转封装 → 已完成。以前这里标成 `paused`，于是面板写着「已暂停」而下载目录里
  躺着没人认领的 `.ts`；退出应用时更糟，状态被覆盖成 `paused` 而线程还在转封装，进程一断
  就留下半截文件。想重来请用「取消」（明确丢弃已录内容）。
- **进度列说的是「已录多久」而不是百分比**：没有总量就没有百分比。`已录 12:30`，设了上限时
  再跟一句 `· 剩 5分0秒`，没设上限时不编造剩余；引擎还在 `Waiting`（直播没开始 / 分片没生成）
  时显示`等直播开始…`而不是一个不动的百分比。录完之后按普通任务显示（那时该看大小和完成时刻）。
- **ffmpeg 引擎碰到直播直接说清楚**（`auto` 也不再退回它）：ffmpeg 只会跟着清单一直拉，
  而直播清单永远不写完，任务就挂在那里不结束。理由写进错误文案，让用户去改
  `stream_engine`，比给一个永不完成的任务诚实。
  *（Windows 包同样是这条通道：`build-windows.yml` 用同一份 `zdm/zdm.spec` 打 PyInstaller，
  带上的就是同一套 Python 核心与 `bin/N_m3u8DL-RE` —— 界面里那句「三端同一套」不是修辞。
  仓库里那份 `windows-native/` C# 核心只是留档，Windows 安装包早就不构建它了。）*
- **引擎中途才认出直播时的兜底只认原句**（`WARN : Live stream found`）：按「文案里出现
  live stream」做子串匹配会误伤 —— 引擎在参数报错和帮助回显里也提这个词，一个正常点播任务
  被翻成直播后收尾走错分支，报出「直播没有录到任何内容」这种把人带偏的原因。

边界仍在：DRM / 需要外部解密的流（HLS 加密切片、Widevine / FairPlay）无法下载。

**Windows 安装包在 v1.17.0 那次没能构建出来** —— v1.17.1 修的是构建脚本自己：
`fetch_bin.py` 的进度文案是中文，而 Windows 控制台默认是代码页（CI 上 cp1252），
`print` 抛 `UnicodeEncodeError` 让**已经下载成功**的那一步非 0 退出，整个 Windows 作业
红在「下载 deno 失败」这种看着完全无关的行上。现在这两个构建期脚本把输出流统一改成
UTF-8（`errors="replace"`），`--selfcheck` 的 JSON 打印同理。功能代码没变 ——
v1.17.0 的 mac / Linux 包和 v1.17.1 完全一致。

**桌面端「设置按钮不见了」** —— v1.17.3 起（代码 `b1a4158`，随本版第一次发布）：`QToolBar`
装不下时不会截字，而是自己弹出一个「>>」把放不下的按钮收进菜单 —— 而没人会去点那个箭头，
于是现象就成了「设置入口没了」。实测默认宽度下「打开目录」「设置」已经被收走，再窄一点
收起四个、五个，而第二行（筛选条）右侧一直空着四百多像素。现在把「清除已完成 / 打开目录 /
设置」挪到筛选条右侧，按动作层级排：列表动作 → 队列动作 → 应用入口。挪完核对过两件事：
任何合法宽度下都不再出现「>>」；第二行需求 888px 小于窗口最小宽度 912px，不会被截字。

**AriaNg / Motrix 那一类 aria2 客户端管不了 ZDM** —— v1.18.0 起，本机服务在**同一个端口**上
多认一条 `POST /jsonrpc`（别名 `/rpc`），说的是 aria2 的那套 JSON-RPC：填上地址 + RPC Secret
就能添加 / 暂停 / 继续 / 删除 / 排队 / 改全局并发与限速。

- 它只是一层翻译：任务进的还是同一个队列、同一条事件流。不会出现「RPC 加的任务界面里没有」
  这种两套状态各活各的 —— 视频页面链接照样转 yt-dlp、站点 Cookie 照样兜底、重复下载照样拦。
- 鉴权按 aria2 的约定：`params[0]` 允许是 `token:<口令>`；也照旧认 `X-ZDM-Token` 头、Cookie、
  `?token=`。用的就是本机接口那同一枚令牌，不另发一套 credential。`aria2.checkToken` 在鉴权
  之前处理（令牌错也不报错，只把收到的原样带回）—— 那是 aria2 特意留出来给客户端自查的口子。
- **CORS 只对 `/jsonrpc` 放开「回显请求 Origin」**，其它路径一律不变。敢放的前提是三条同时成立：
  服务只绑 127.0.0.1、每条调用都必须带令牌、`Host` 校验仍挡 DNS rebinding。AriaNg 通常跑在
  另一个端口上，不放这一条就是「连得上、读不到响应」，比 401 更难查。
- 口径照 aria2：长度 / 速度全部是**字符串**；`tellActive` 里含 paused 与 canceled
  （`canceled → paused`）；`remove` 对正在下载的任务先报错、`forceRemove` 才放行；删除一律
  **不碰磁盘文件** —— 兼容层不该替用户删掉已经下好的东西。
- `system.multicall` 必须可用（AriaNg 每次刷新发的就是它），并禁止嵌套；`system.listMethods`
  列出来的每个方法都真的可调。
- 做不到就说做不到，不「假装成功」：BT / 磁力 / Metalink 直接拒；不认识的 aria2 选项
  （`ftp-pasv`、`bt-max-peers`…）报错而不是收下再忽略；`changeOption` 只允许改连接数，改
  `dir` / `out` 会被拒 —— 那两个动的是已经落盘的路径。
- 队列位置：ZDM 的排队顺序由优先级决定（±99 共 199 档），`changePosition` 靠重发一整条优先级
  梯子实现；排队任务多于 199 条时明确报「无法保证精确位置」，而不是给一个错的顺序。
- 开关是设置里的「兼容 aria2 JSON-RPC」（`rpc_enabled`，默认开），三端都能看到并复制地址与
  令牌（网页版走 `GET /api/token`，桌面端在设置对话框）。关掉只是不认这条路径，`/api/*` 照旧。
  端口改了没重启时，网页版会点破「服务当前实际在听的端口」—— 复制一个连不上的地址，用户只会
  怀疑令牌。
- 一次真实的连带伤害：给 RPC 让路时把 `_api_post` 的尾巴挤成了死代码，于是
  「点保存没反应」—— GET 全好、POST 一律没响应，肉眼最难归因。回归脚本里现在有一组
  「每个 POST 端点都必须真返回点什么」的断言。

**只有 http/https 下得了** —— v1.18.0 起 `ftp://`、`ftps://`、`sftp://` 进的是同一台引擎、
同一个队列、同一套分块与断点续传，不是另开的第二条通路（桌面端、网页版、扩展、CLI、aria2 兼容层
五处入口都认）：

- FTP/FTPS 只用标准库（`ftplib` + `ssl`），装完即用，不额外带依赖。
- 长度问 `SIZE`、续传用 `REST`。**REST 的回复必须自己看过**：ftplib 的 `ntransfercmd(rest=...)`
  会把服务器对 REST 的答复丢掉，碰上「嘴上答应、实际从头发」的服务器，写出来的是一条长度刚好、
  内容全错的文件 —— 这种损坏比报错难发现得多，所以这里只认 3xx 回复。
- 服务器不配合就如实降级：不认 `SIZE` 显示「大小未知」，不认 `REST` 退回单流顺序下载，
  绝不假装能续传。
- `ftps://` 默认显式 `AUTH TLS`（21 端口，与 curl 一致），端口写成 990 才走隐式 TLS。
  证书校验不打折：自签、链不完整一律连不上，不会「当成明文先把文件下完」。
- SFTP 需要 `paramiko`（SSH 握手绕不开密码学实现，标准库没有）。三端安装包内置，源码安装由
  `install.sh` 顺带装上；确实没有的机器在**添加链接那一步**就被拒绝，同时说清缺什么、怎么补，
  而不是建一条永远下不完的任务。
- 主机密钥按 TOFU：首次连接记进 ZDM 配置目录里的 `sftp-known_hosts`，**不碰用户的
  `~/.ssh/known_hosts`**；之后同一主机密钥变了直接拒绝 —— 可能是中间人，也可能是服务器重装，
  两种都不能「先下完再说」，回执里会写清怎么确认、删哪一行能解除。
- 一条要说在前面的限制：**设置里的代理只对 http/https 生效**，ftp/ftps/sftp 走各自的协议通道。
- 协议白名单只有一份（`zdm/zdm/transport.py` 的 `SUPPORTED_SCHEMES`），后端、桌面端、网页版
  都读它 —— 免得某一层放行了 ftp、另一层还在报「只支持 http/https」。

**状态栏右下角那个版本号不是扩展的版本** —— v1.18.0 起（扩展 1.5.43）：「● 扩展已连接」后面跟的是**扩展自己
报的版本**（新增 `X-ZDM-Ext-Version` 请求头 → 服务端 presence → `/api/extension.ext_version`），
桌面端的标签则写明 `ZDM v1.x.y`。扩展没报过版本（装的是旧扩展）时那一栏什么都不加，不编一个
数字出来。

**扩展只有 Chrome 能用** —— v1.18.0 起 Firefox 也认，而且**仍是同一份 `extension/` 源码**：
`zdm/zdm/firefox_ext.py` 只翻译清单（去掉 Chrome 的 `key`/`minimum_chrome_version`/`downloads.open`，
把 `background.service_worker` 换成 `background.scripts`，补上 `browser_specific_settings.gecko.id`），
再在内存里打成 `.xpi`。不复制第二份 JS，就不会出现「Chrome 修了 bug、Firefox 还带着坏版本」：

- 三个入口拿同一个包：桌面端「浏览器扩展 → 导出 Firefox 扩展」、网页版底部的
  `GET /api/extension/firefox.xpi`（服务端现场打包）、`zdm firefox-ext --out x.xpi`。
  **不在仓库里预存第二份**，磁盘上那份 `extension/` 永远是唯一真相。
- 也没有第四个 Release 资产：包是按需生成的，每个 Release 仍然只有 4 个文件。
- 真正的坑在 API 命名空间：Firefox 的 `chrome.*` **只有回调、不返回 Promise**（Promise 形式挂在
  `browser.*`），`await chrome.tabs.get()` 在那边拿到的是 `undefined`，接着读 `.url` 就是一片
  「读不到属性」的崩溃。所以扩展里凡是按 Promise 用的调用统一走 `EXT_API`（有 `browser` 就用它，
  否则用 `chrome`），事件注册与回调式调用继续用 `chrome.*` —— 两边那一套都是通的。
- 原生消息主机一份清单喂两家：`allowed_origins`（Chrome 系）与 `allowed_extensions`（Firefox）
  写在同一个 `com.zdm.launcher.json` 里，各家忽略各家不认的那个；`.deb`、Windows 安装脚本和
  `install.sh` 都会把 Firefox 那棵树/目录一并注册。Firefox 的扩展 ID 只在

**v1.18.9 = 「继续」不再把任务换成新名字** —— v1.18.8 之后拿真机走了一遍暂停/继续，翻出一个小而狠的老问题：
单流任务（`-c 1`，或者服务端不支持分块）没有分块器，每次重新开始都要重新探查一次，而探查之后那行
`filename = _unique_name(directory, filename)` 会去看目录里有没有同名文件 —— 它看见了 `xxx.bin.part`，
以为撞了别人的名字，于是把任务改成 `xxx(1).bin`。后果不止难看：旧的半截文件当场变成没人认领的孤儿
（已下的字节作废，进度从 0 重新爬），再暂停一次就变成 `(2)`，而「删除」只删得掉当前名字那一份，
前几份永远留在下载目录里。重启服务也会踩同一脚：`state.json` 里记的名字和目录里那份 `.part` 对不上，
续传变成重下。修法是给这次改名把「自己那份 `.part`」排除在冲突之外（`skip=self.part_path`）：
目录里躺着别人的同名文件或同名 `.part` 时照旧让位，绝不覆盖用户已有的文件。离线用例 16 条断言，
服务器限速到 2 MB/s 让暂停窗口稳定：两轮暂停/继续后名字仍是 `reproC.bin`、目录里始终只有一份 `.part`、
进度接着往上走、删除后不留孤儿，进程内重启（`save_state` → 新 `Manager`）同样不改名；
纯函数口径另外钉住「同名成品要改名」「同名 `.part` 是别人的也要改名」「`skip` 指到自己身上才不改名」。

**v1.18.8 = 「删除」不再谎报失败** —— 点删除时，`Manager.remove()` 把 HTTP 请求线程挂在原地：
先 `_wait_idle` 等 worker 退出（最坏 12 秒），再删 `.part` / `.meta` / 成品、回收 `re-work/<id>`
分片目录、写 `state.json`；暂停更久，`Download.pause()` 自己还要先 join 一轮连接线程（默认 15 秒）。
而命令行 10 秒、桌面端 8 秒就超时 —— 于是服务端明明删干净了，界面回一句
`service not reachable: timed out`，用户以为没删掉，只能反复点。现在请求线程只等 3 秒
（`Manager.SETTLE`）：列表和 `state.json` 当场更新（这才是用户要的结果），等 worker 退出、删文件、
回收分片目录挪到后台线程 —— 它有的是时间，而且能等到句柄关掉再删，Windows 上「文件被占用所以删不掉」
顺带一起解决。`_wait_idle` 现在如实返回「等到了没有」，没等到就把这一步在后台重做一遍，
而不是默认线程已经停了。继续 / 重下撞上还没退出的 worker 时同样先回话、等干净了再入队
（两拨线程写同一个 `.part` 是会写坏的）。删除一条正在下的任务，界面上关于它的事件只剩
`added → removed`：已删的行不会被 worker 收尾时补发的 `canceled` / `progress` 画回来。
`shutdown()` 退出前给这些收尾线程 1.5 秒 —— 预算刻意这么短，因为 v1.18.3 的教训是等过头会被
launchd 记成「Python 意外退出」。命令行与桌面端也把「超时」和「服务没起」分开写：前者说
「操作可能已经生效，刷新列表确认」，不再让人以为程序坏了。离线用例用一个卡住 8 秒的假 worker
把边界钉住（21 条断言：`remove` 在 1.5 秒内返回、状态与 `state.json` 立刻一致、`.part` 在 worker
收工后被清掉、`pause` 不等满 8 秒、`resume` / `restart` 先回话后入队、`shutdown` 等得到收尾线程）。

字段一项没增减：离线用例把保存的 15 个键、旧配置回填、「取消不发请求」「归档规则写错先本地拦住」
钉住（23 条断言），网页端整页英文渲染零残留中文。

**v1.18.6 = 删除已不在列表里的任务时，命令行回「error: None」** —— 本机实测里连着删两次同一条任务
（第一次客户端超时、其实服务端已经删成），第二次屏幕上出来的是 `error: None`。理由只有一个：
`DELETE /api/tasks/{id}` 在没找到任务时回的是光秃秃的 `{"ok": false}`，没有 `error` 字段，
而 CLI 直接把那个字段打了出来。看着像程序自己坏了，实际只是「这条任务已经不在了」。
现在服务端补上 `404 没有 ID 为 xxx 的任务（可能已经删掉了）`（网页端的英文界面同步收录这句），
命令行也不再假设服务端一定写了理由 —— 任何 `ok:false` 的响应，取不到理由就打一句人话而不是 `None`；
批量展开里单条失败、`zdm stop` 撞不上服务这两处同样按这个口径改过。

**v1.18.5 = B站的收藏夹 / 合集 / 稍后再看没被当成清单** —— v1.18.4 说「清单地址会被拒绝并改走展开」，但那份
判定表里 B站只认 `space.bilibili.com/<uid>`（投稿）、`/channels/…`、`medialist/`、`list/`、`favorite/`，
用户实际从网页地址栏复制来的却是 `space.bilibili.com/<uid>/favlist?fid=…`（收藏夹）、
`…/channel/collectiondetail?sid=…`（合集）和 `www.bilibili.com/watchlater/`（稍后再看）。
这三类当时会被认成「普通网页」，建成一条任务后由 `[generic]` 提取器接住：要么整串失败，
要么只拿到页面上第一集 —— 正是这次要消灭的那种「看起来成功了」。补法是按随包 yt-dlp
2026.08.19 的提取器对齐：`BilibiliFavoritesList`（favlist）、`BilibiliCollectionList`（collectiondetail）、
`BilibiliSeriesList`（seriesdetail）、`BilibiliWatchlater`（watchlater）四类形态都归进清单这一类
（每条都用 `yt-dlp -v --simulate` 确认过落到哪个提取器上），`dynamic` / `homepage` 这些不是视频清单的
标签页继续排除在外。判定表的用例（18 条形态 + 42 条地址的漂移检查）与展开实现一起跑，
不改解析与建任务那条通路。

**v1.18.4 = 一份清单只能下成一集** —— 以前把 YouTube 播放列表或 B站收藏夹地址交给「＋下载」，
任务会「成功」，目录里只剩最后一个文件：yt-dlp 对播放列表输出的是**固定文件名**，一集盖一集。
`--no-playlist` 也救不了纯清单地址（那里没有单个视频可退）。现在三端都有展开入口
（桌面端 / 网页版「播放列表…」、`zdm playlist` 与 `zdm add --playlist`），一份清单变成 N 条独立任务，
每条有自己的名字、自己的进度、自己的重试；单条建任务那条路对清单地址直接回 400 并写明该走哪个入口，
不再让「已完成」骗人。名单默认 100 条、硬上限 500 条，截断与否都写在界面上，
范围解析（`all` / `1-20` / `1,3,5-8`）三端共用 `yt_playlist.parse_range` 一份实现。

**v1.18.4 = 下完的东西散在下载目录根上** —— 新增「按后缀自动归档」（`archive_rules`，**默认关闭**）：
`mp4,mkv,webm = Video` 每行一条，命中的成品进 `<下载目录>/Video`。三个设计决定值得记下来：
① **只在真正开跑那一刻取规则**（`manager._run_task`），不是建任务那一刻——设置改了要对之后的下载生效，
而不是一改就把排队中的任务目录改掉；② **只决定「落在哪儿」，不决定「落不落盘」**，字幕 / 额外音轨这类
sidecar 永远跟着成品走，不然 `.srt` 进 Subtitles、`.mkv` 进 Video，用户得自己配对；③ **子目录只能是
相对路径**，`/Volumes/x`、`D:\Video`、`~/x` 当场拒绝（把 `D:\Video` 硬改成 `<下载目录>/D/Video` 是猜，
报错才是答），写坏一行不会连累整份设置：写入侧 `normalize_rules` 严格、读取侧 `prune_rules` 丢坏行留好行。
没归档成功不静默回退原目录，而是在任务上留一句 `archive_note`（桌面端悬停、网页版橙色提示、`/api/tasks`）。

**v1.18.3 = macOS 反复弹「Python 意外退出」** —— 症状是桌面端隔几十秒弹一次系统崩溃框（进程名
写作 Python），同时 `zdm.log` 里同一个「端口 9000 已被占用」能刷上千行。根因是 LaunchAgent 的
`KeepAlive` 写成了无条件 `true`：`.app` 和这个 agent 都想当「占用 9000 的那个唯一实例」，抢不到端口的
那个进程**正常退出 0**，而 `true` 的意思是「退出 0 也再拉一次」——于是 launchd 每 10 秒重起一个必然秒退
的 Python（本机实测一晚上 `runs = 191`），并把这种「不是自己停的」退出记成 `crashed`，用户看到的就是
弹窗。现在 `KeepAlive` 改成 `{ SuccessfulExit = false }`（只在真失败时重启）+ `ThrottleInterval = 20`。
配套把退出码本身也修诚实：`zdm serve` 端口被占时先探一次，占着的**是**健康 ZDM 才退 0，占着的是别的程序
退 1 并说清「ZDM 起不来」——否则改成「只在失败时重启」之后，真故障会变成静默不起服务。Linux 的
systemd 单元本来就是 `Restart=on-failure`，这次是让 macOS 与它对上。

**v1.18.2 = macOS 上 Firefox 的原生消息主机** —— 本机实测：`/Applications/Firefox.app` 明摆在，
`install.sh` 却把 Firefox 那一半跳过了，因为「装过 Firefox 才写」的证据取的是
`~/Library/Application Support/Mozilla` 是否存在 —— 而这棵树在装了 Firefox 的 Mac 上常常从没建过
（用户数据全在 `…/Firefox` 里）。表现只是「ZDM 没开着时扩展唤不醒它」，联不到安装脚本这一层。
证据改成三选一（`…/Firefox`、应用包、`…/Mozilla` 任一命中），命中就 `mkdir -p` 出 Firefox 真正读的
`…/Mozilla/NativeMessagingHosts`。Linux 侧本来就是 `~/.mozilla` 判断，不受影响。

**v1.18.1 = v1.18.0 的 Linux 包** —— v1.18.0 那次 CI 只有 mac 的 `.dmg` 和 Windows 的 `.exe` 出来了，
`.deb` 与便携 `.tar.gz` 缺：`build_linux_app.sh` 里新加的「脚本内 Firefox 扩展 ID 必须和
`firefox_ext.py` 的 `GECKO_ID` 一致」那条断言写成了 `BAD="$(... | grep -vx "$GECKO_ID" | sort -u)"`，
而脚本开头是 `set -euo pipefail` —— **一切一致时 `grep -vx` 恰好没有输出、返回 1**，pipefail 把这个
非零状态带出命令替换，赋值语句自己就成了失败命令，于是这条防线在「没有问题」的那条路上把整场构建
静默杀掉（日志停在 `==> staging the .deb`，一行错误都没有）。补法是断言末尾 `|| true`，并且本地用
两种情况各验一遍：ID 全对时脚本继续、真抄错时照样报出来。写在这儿是因为这类坑长得都一样：
**用「找不到差异」来表达「通过」的命令，在 `set -e` 下就是一个只在坏情况下才不炸的反向断言。**

**每次失败的具体原因会写到** `download-errors.log`（Windows：`%APPDATA%\ZDM\`，
Linux：`~/.config/zdm/`，macOS：`~/Library/Application Support/ZDM/`）。
排查时先看这个文件，再对比版本号。

## macOS：真正的原生 App（v1.11.0 起）

`ZDM.app` 的主程序 `Contents/MacOS/ZDM` 是**用 clang 编译的原生 Mach-O**（源码 `zdm/zdm_launcher.m`），
它通过 Python C API 把CPython 解释器内嵌进 App 自身的进程，再运行 Qt 客户端——全程只有一个进程，
而且这个进程就是 `ZDM.app` 本身。

这样做是为了保住 macOS 应用身份：早期版本用「shell 脚本 + exec python」的方式启动，进程镜像会变成
`Python.app`，导致 Dock 显示通用占位图标、点 Dock 图标唤不回窗口（菜单栏托盘不受影响，因为那是
Qt 自身的逻辑）。改成原生主程序后，Dock 图标、点击唤回窗口、`applicationShouldHandleReopen:`
全部按 macOS 原生方式工作。

安装脚本会自动完成：编译 launcher → 把 `Python3.framework` 嵌入 `Contents/Frameworks/` →
生成完整 icns 图标（含全部 @1x/@2x）。若系统没有 clang，会自动回退到脚本启动器（功能可用，仅 Dock 行为受限）。

## 功能

- 多线程分块下载（动态切分，空闲连接抢占最大剩余块）。单任务连接数上限 32：
  `_run_segmented` 是按连接数直接开线程的，`zdm add -c 9999` 以前会真的开出
  几千个线程和几千条 HTTP 连接，现在统一夹到 1~32，命令行会写明「连接数按上限 32」
- 断点续传、暂停/继续、跨进程重启续传
- **按后缀自动归档**（v1.18.4 起，**默认关闭**）：设置里写几行 `mp4,mkv,webm = Video`，
  命中的成品落进「下载目录/子目录」，没命中的照旧；字幕 / 额外音轨这类附带文件跟着成品走，
  不单独归档。三端同一套解释（桌面端设置页、网页版设置、`zdm config archive_rules "mp4 = Video"`），
  规则文本和 `{"mp4": "Video"}` 两种写法都收。**自动归档只决定之后的下载落在哪儿**，
  已经下好的文件要靠下面那条「整理」入口，不会因为你改了规则就被自动重排。
  子目录只能是下载目录里的相对路径：写成 `/Volumes/xxx`、`D:\Video` 或 `~/x` 会被当场拒绝
  （把它硬改成 `<下载目录>/D/Video` 是猜，报错才是答）；同一个后缀出现在两条规则里也当场拒。
  没按规则归档成功时不会静默改回原目录 —— 任务上会留一句理由（桌面端状态列悬停、
  网页版任务行橙色提示、`/api/tasks` 的 `archive_note`）
- **把归档规则补到已经下好的文件上**（v1.18.11 起）：桌面端设置页、网页版设置页都有
  「整理已经下好的文件…」，命令行 `zdm archive`（默认只列清单，`--apply` 才真搬，
  `-o DIR` 换目录，`--json` 出报告），HTTP 侧 `POST /api/archive/sweep`。清单先摆出来、
  确认了才动手；还在下载 / 暂停 / 排队中的任务持有的文件一律不碰，只整理这一层不再递归，
  目标撞名只跳过**不自动改名**，落点出不了下载目录。搬成功的文件会把任务记录里的新路径
  一起改掉（「打开文件」不会还指着老位置），一次最多 5000 个，超了会写明可以再点一次
- 队列与同时下载数限制、全局限速
- **任务中途改链接 / 请求头 / 代理**：正在下载的任务也能改 URL、Referer / Cookie / UA、
  代理、连接数、优先级与定时时间。已下载的分块保留，重启时核对新地址的文件长度：
  一致就续传，不一致才自动从头下载（不会把两个文件的字节拼在一起）
- **定时开始与优先级队列**：新建、批量导入和「修改任务」都能设开始时间与优先级。
  优先级高的先出队（桌面端列表用 `P+5` 徽标标出，网页版写在任务副标题里）；
  定时任务到点才开始。「全部暂停 → 全部继续」会保留原定时间
- **批量导入**：桌面端工具栏「批量导入」与网页版「批量…」可一次粘贴多行链接
  （空行和 `#` 注释自动跳过），优先级 / 定时开始在对话框里当面对好，
  不会悄悄套用输入条上残留的值
- **播放列表 / 合集批量下载**（v1.18.4 起）：把 YouTube 播放列表、频道投稿页，或 B站的投稿 /
  合集 / 收藏夹 / 稍后再看地址交给桌面端「播放列表…」、网页版「播放列表…」、
  `zdm playlist <链接>` 或 `zdm add <链接> --playlist`，会**展开成一条条独立任务**：
  先列名单（标题 + 时长），再按 `all` / `1-20` / `1,3,5-8` 挑要下的，可选「收进以清单标题命名的
  子目录」、优先级与定时开始。展开上限默认 100 条、最多 500 条，名单被截断时会写明「按上限 N 条截断，
  后面还有没列出」，不会出现「界面只列出 100 条、选到 150 就报错」这种自相矛盾的名单。
  **清单地址直接建成一条任务会被拒绝** —— yt-dlp 对播放列表固定输出同一个文件名，一集覆盖一集，
  最后只剩一个文件；所以三端入口都强制走展开，报错里也直接写出该用哪个入口。
  批量导入里混进清单地址时，只点名有几个是清单、不擅自展开（展开一份频道投稿页要翻几十页、
  等几十秒，静默卡在「导入」按钮后头不合适）；整批都是清单时才直接进展开对话框。
  加 `--no-subdir` 就并进 `--dir` 原目录，范围写法 `zdm add <链接> --playlist 1-20,25` 与
  网页版 / 桌面端同一套解析；先看清名单再决定下不下，用 `zdm playlist <链接>`（只列名单不建任务）。
- **视频选段下载**：YouTube / B站 等视频页任务可只下一段（如 `00:01:00-00:05:00`），
  桌面端、网页版、CLI 都支持；成品名带区间，同一视频下多段不会互相覆盖。
  普通文件链接填选段会被明确拒绝（而不是静默下整包）。区间写法在服务入口就校验：
  写反（结束早于开始）、写成 `5min` 这类当场回 400 说清格式，不会再拖到 yt-dlp
  跑完才发现「退出码 0 却没有文件」；旧记录里没带 `*` 的写法也能正常下载
- **剪贴板监听（默认关闭）**：复制 http(s) 链接后自动填入新建下载输入框，
  需要回车确认才开始下载，不会偷偷建任务
- **GitHub / Hugging Face 镜像加速（默认关闭）**：Release / 归档 / raw 文件走 gh-proxy，
  模型文件走 hf-mirror；镜像站限流或挂掉时自动退回原地址，已下载分块继续用
- HTTP/2-only CDN 自动回退 curl 传输
- 桌面端单实例 + 系统托盘（右键含「开机自启」「退出」）
- 桌面端工具栏可一键「打开网页版」
- **每个任务行都有暂停 / 继续**：每行操作区最前面是 `⏸` / `▶` 图标按钮（主题感知绘制，
  深浅色都清晰），针对单个文件；已完成的行保留同位置的按钮但置灰（没有可暂停的东西），
  按钮不会随状态忽隐忽现
- **「全部暂停 / 全部继续」在主界面**：筛选标签右侧的中文按钮（`⏸ 全部暂停`、`▶ 全部继续`），
  没有可操作任务时自动置灰；托盘与右键菜单里也保留同名项
- **菜单栏图标弹出的是毛玻璃菜单**（macOS vibrancy）：背景模糊菜单后的内容、12px 圆角，
  浅色/深色自动匹配（VibrantLight / VibrantDark）；其它平台自动退回不透明菜单
- **「打开」打开的是文件本身**：下载完的 `.dmg` 双击直接进安装界面、`.pdf` 用默认阅读器打开；
  另设「目录」按钮 / 右键「在文件夹中显示」，用于定位文件
- **下载时自动拉起桌面端**：桌面端没开时，浏览器扩展（或 `zdm add`）把任务交给本地服务后
  会自动打开 ZDM 窗口；已在运行则直接激活。可在「设置」里关闭
- **版本号可见**：窗口标题、状态栏右下角、托盘提示、关于对话框都显示当前版本
- **更新提示 + 一键更新**：启动时静默检查 GitHub Releases，有新版本会在主界面顶部弹横幅
  （下载并安装 / 更新说明 / 忽略此版本），自动下载对应平台的安装包并打开安装程序；
  也可在「设置 → 立即检查更新」或托盘「检查更新」手动触发
- **深色 / 浅色模式**：默认**跟随系统外观**自动切换（macOS 读 AppleInterfaceStyle、
  Windows 读 AppsUseLightTheme、Linux 读 gsettings），也可在「设置 → 外观」手动锁定为
  浅色或深色。所有颜色统一取自一套调色板（`zdm/theme.py`），深浅两套完全一致，
  切换时表格、进度条、状态色等自定义绘制部分同步刷新，不留异色碎片。
- 浏览器扩展一键接管下载
- **视频 / 音频嗅探（一键推送下载）**：装好扩展后，网页右下角会出现 ZDM 浮动按钮，
  角标显示当前页面嗅探到的媒体数量。点开面板列出每一个视频 / 音频（图标区分、显示文件名与大小），
  点「推送」即交给 ZDM 下载。嗅探有两条来源并会合并去重：`webRequest` 响应头
  （能看到 Content-Type 与大小，覆盖播放 / 拖进度条 / 切清晰度时的请求）+ 页面 DOM 扫描
  （覆盖首屏就摆在那儿的 `<video>` / `<audio>` 直链媒体）。
  任务列表会标出来源（`[嗅探]` / `[浏览器]` / `[网页版]` / `[协议]`），顶部有「嗅探」筛选。
  *（HLS `.m3u8` / DASH `.mpd` 这类自适应流不进嗅探列表——它们是分片协议，列出来点了也
  只是个清单。把 `.m3u8` / `.mpd` 地址交给「＋下载」或 `zdm add`，会走流媒体通道：
  分片并发拉取 + 合流，见下方「流媒体下载」。直播与自适应视频页仍走「解析此页面」，由 yt-dlp 处理。）*
- **流媒体下载（HLS `.m3u8` / DASH `.mpd`）**：默认引擎是随包内置的 **N_m3u8DL-RE**
  （MIT，单文件、自带 .NET 运行时），它按分片并发下载、单片失败自动重试，暂停后**按分片续传**
  ——下次接着下已完成的分片，不再从第一个切片重来。设置里可选 `自动`（找不到它就退回 ffmpeg）/
  `只用 N_m3u8DL-RE` / `只用 ffmpeg`（`zdm config stream_engine re`）。凡是没用上你选的那个引擎，
  任务上会写明理由（桌面端状态列的悬停提示、网页版任务行的橙色提示、`/api/tasks` 的 `stream_note`），
  不静默降级。限速、代理、Cookie / Referer 都会带给引擎；DASH 的音视频分轨场景仍由 ffmpeg 处理。
  *（多音轨 / 多字幕可点名：轨道选择框在桌面端新建与编辑对话框、网页版地址条下方的轨道条、
  `zdm add --select-video/--select-audio/--select-subtitle/--sub-format` 三处都有，写法见
  上方「多音轨的 m3u8」一条。粘贴 `.m3u8` / `.mpd` 地址本身就按流媒体任务处理，不需要额外声明。）*
  *（**还在播的** `.m3u8`（清单里没有 `#EXT-X-ENDLIST`）自动按直播录制跑：进度列显示「已录多久」，
  可设录制时长上限（`zdm add --live-limit 30:00`，界面里同一项在轨道选择那一块），随时点「停止
  录制」都会把已经录下的那段封成成品；直播没有「暂停」，所有暂停入口对直播都等于停止录制。
  写法见上方 v1.17.3「`.m3u8` 是还在播的直播」那一条。）*
- **视频卡片上的「下载此视频」按钮**：B站 / YouTube 的每个视频卡片右上角，鼠标移上去
  会浮出一颗按钮，点开是该视频的**清晰度列表**（1080P / 720P / 音频…），选一个直接推给 ZDM。
  扩展就地解析页面里已加载的媒体数据（YouTube 的 `streamingData`、B站的 `__playinfo__`），
  不额外发请求。DASH 的画面与声音是分开的，ZDM 下载后用随包的 `ffmpeg` 合成有声音的视频
  （三端安装包都内置 `bin/ffmpeg`，不再依赖用户自己装；真缺了会在任务上写明「无声音」而不是静默成功）。
- **任意网站播放器上的「下载此视频」按钮**：除 B站 / YouTube 外的所有页面，播放器右上角
  都会浮出同一颗按钮（不写任何站点规则，靠「页面里哪个视频最大、哪个在播」定位）。
  点开有三条路径，按「有没有声音」排序：
  1. **解析此页面**（推荐）：把页面地址交给后端 yt-dlp，返回的就是合好音的格式列表，
     可选清晰度。DASH 站点也有声音，覆盖 2000+ 平台；
  2. **下载视频 + 音频**：嗅探同时抓到视频轨与音频轨时，两条一起推给后端 ffmpeg 合流，
     作为 yt-dlp 不认识站点时的兜底。是否可用由按钮上的「可用」标记实时反映；
  3. **直接下载当前视频**：只用播放器正在播的那条地址，可能只有画面（按钮会说明）。
  播放器走 MSE 加密串流（`blob:` 地址）时第 3 条自动不可用，并提示改用第 1 条。
- **图库 / 壁纸 / 音乐站**：嗅探面板右上角「扫图片」按需扫描页面里的大图
  （含 `srcset` 原图与指向原图的链接，过滤图标 / 头像），可勾选**批量下载**；
  音乐站的音频条目按原格式（mp3 / m4a / flac）下载。
- **未启动也能接管**：ZDM 没开着时，浏览器里点下载会**自动把它拉起来**再接手任务
  （Windows 通过 Native Messaging → `ZDM-NativeHost.exe`，其他平台靠协议唤起）
- 开机自启（设置里可勾选，macOS / Windows / Linux 三端均支持）

详见 [`zdm/README.md`](zdm/README.md)；macOS 踩坑与修复记录见 [`docs/ZDM_安装与使用说明.md`](docs/ZDM_安装与使用说明.md)。
